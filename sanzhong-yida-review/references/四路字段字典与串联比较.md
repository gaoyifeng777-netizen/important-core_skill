# 四路字段字典与串联比较

版本：1.1；适配提取输出 schema 1.1、判定输出 schema 1.3、Skill 1.0.0。本文是任务提示词的组成部分，不是客户制度。

## 1. 分工与赋值原则

四个识别 Agent 共用字段定义，各自只对自己的原件赋值。允许共用字典，不共享答案。`meeting_schedule` 读取清单/通知/议程；`proposal_extract` 读取议案审批和事项附件；`meeting_record` 读取原始记录；`meeting_minutes` 读取纪要/决议。共用字段不扩大材料白名单。

`tags` 表示这条事实属于哪类；`values.items.field` 表示具体比较什么；`raw` 保留原文；`normalized` 只做无歧义格式整理；`qualifiers` 保留金额口径、人员身份等限制；`evidence_indexes` 指向同条记录的原文证据。每条记录仍保留 fact_state、subject_ref 和完整句意。

编号由主控或角色生成，评价人员不需手填。字典值来自材料，不能由主控批量补齐、按规则期待反推或把空值改成零。没有提取到某字段与原件没有记载是两回事，缺口通过 field_checks 和 requests 表达。

## 2. 每条值的固定形状

```json
{
  "field": "financial.amount",
  "raw": "人民币100万元",
  "normalized": "100",
  "qualifiers": {
    "currency": "CNY",
    "unit": "万元",
    "amount_basis": "投资上限",
    "scope_raw": "A项目一期",
    "tax_basis": "unknown",
    "bound": "cap",
    "stage": "decision"
  },
  "evidence_indexes": [0]
}
```

以上为虚构格式示例，须有同 record.evidence[0] 的对应原文才能使用。raw 应是所引用证据中的连续原文；限定信息也必须由同条证据支持。正文条件应另提 condition.content 并与决定关联，不能因已摘金额而丢掉条件。每条实质记录至少一个 items 项；未覆盖的新类型用 fact.other，不擅加字典键。

- 文本：normalized 默认 null；确需整理只去除排版空白，不改机构名、标题、结论或否定。别名对应由判定者核实记录。
- 金额：normalized 用十进制字符串保留原数，不乘单位；currency 原文明示人民币才用 CNY，未明示为 null；金额属性/税口径/范围/阶段不同，不能直接等值比较。范围、模糊数量不取单值。
- 人数/票数：整数也用字符串；只识别明示数，不能把“一致通过”赋值成应到人数；unknown 不等于零。
- 时间：完整日期可格式化；缺年不按任务年份补齐。年月精度不得补日，日期精度不得补钟点；relative/unknown 的 normalized 为 null。event_type 由日期字段固定映射，不自造。
- 每条日期 items 必须在 time_index 出现且只出现一次，增加 item_index（从0开始）。raw、normalized、precision 必须与指向项一致。time_index 仅是索引，不建立第二套时间事实。
- qualifiers 的键必须恰为字典所列；未知按定义用 null/unknown。空 qualifiers 用 {}。不能把规则判定、别的角色结论塞入附加字段。
- 每轮输出写 dictionary_version=1.1、schema_version=1.1。旧版本成果保留原状；需要本字典比较时按新任务重新提取，不由主控静默改写旧答案为新格式。人工校对迁移须另存版本并标明不是独立重新识别。

### 2.1 金额与条件的语义边界

原文“QL-A1项目拟申请投资上限120万元”分别落位为 amount_basis="投资上限"、scope_raw="QL-A1项目"、stage="requested"、bound="cap"。金额性质、事项范围和业务阶段是三个不同维度；scope_raw 不能填“投资上限”，amount_basis 不能靠 stage 代替。范围未载明留 null，不从任务标题补齐。原文中的申请、估算或历史引述不因出现在纪要里变成当次批准。

condition.content 只表达原文明示约束审议、批准或实施的前提、边界、禁止或例外，并与相应申请/决定关联。议案路“同意提交董事会审议”用 approval.action；“客户需求仍待确认”若只是测算局限用 proposal.analysis；“取得许可后方可实施”用 condition.content。普通处理意见、分析限制和后续安排不能全部归入条件；其他角色只用自身允许字段。语境不足时保留原文和 uncertainty，不自行认定其约束效力或是否履行。

### 2.2 必查项、局部范围与扩展请求

field_checks 是检查完成记录，field 使用本角色必查项名称；records.values.items.field 使用本字典事实字段。present 引用的记录须包含真正支持该必查项的字段，不能只因 record_id 存在就声称已覆盖。程序的角色对应表是有限字段支持检查，不替代原文语义复核。

field_checks 可增加 search_scope（非空字符串）；省略时取同 file_id 的 coverage.processed_scope，其为空才取 assigned_scope。文件 partial 时，已查完局部可以 not_found，未读部分仍保留 not_read/unreadable。相同文件、subject、必查项和实际查找范围不可同时给矛盾状态；不同写法也不能掩盖范围重叠。

requests 保留 file_id、reason、needed_input，可加 request_type（dictionary_extension/material_request）和 record_ids。含 fact.other 的每条记录必须有 dictionary_extension 请求以非空、有效且不重复的 record_ids 引用；其 file_id 为 null 或该记录证据文件。other 标签可用于原文材料差异，不因标签本身要求字典扩展。请求新材料时 file_id=null，在 needed_input 写具体需求，不把尚未提供的资料编入白名单。请求不扩大读取授权。

以上是提取 schema 1.1 的兼容性元数据补充，不增加事实字段。旧结果不通过改写版本号转成新字典结果。

## 4. 由谁串联，按照什么顺序

主控只验收、登记原件、校验格式并交付四份原始成果；不把多路事实预先改写成一张“标准答案”。判定 Agent 读取全部获准成果，依次形成以下三层记录。四路不接收这些记录。

1. **来源关系 links**：先确认是否同一场会议，再确认是否同一事项，以及是否同一次决定/修订；共同计划下不同事项另用 same_group。每条关联保留两端的 `(run_id, subject_ref)`、原文依据与矛盾项；正式事项号是关联线索，不因技术编号相同就合并。
2. **字段比较 comparisons**：针对明确的比较目的，取每端的 `(run_id, record_id, item_index)`，保留原值和换算记录。不得只引用一个没有出处的“金额”列。
3. **业务判定 decisions**：比较结果结合已确认且适用的业务规则、例外及原件核验，形成五类初步结果；comparison_id 回链具体比较，rule_id 回链实际规则。

### 4.1 会议关联与事项关联分开

| 关联层 | 有用线索 | 禁止的推定 |
|---|---|---|
| 同场会议 | 所属单位、会议机构、届次/年度/次数、明确召开信息、文件互引；逐项检查矛盾 | 同一天、同为第5次或主控放同一文件夹就认定同场 |
| 同一事项 | 明确事项号/项目号及其作用域、前后文引用、标的/主体/对象/阶段等；检查编号复用和拆分合并 | 同一标题、金额或相对方就合并；同项目不同采购包自动视为同事项 |
| 同组不同事项 | 明确共同计划、预算或采购需求及成员范围；用 same_group 保留组内关系 | 同组即同一事项；仅因同相对方或临界金额合并；入组就证明有累计义务 |
| 同一次决定 | 同一事项下的会议身份、决策动作、对象范围及版本；审议、批准、调整分别保留 | 申请值与批准值默认应相等；早期批准与后期调整相互覆盖 |
| 版本及历史关系 | 明确补正/替代文号、重新决策材料、有效期间、授权依据 | 文件日期较新必定有效；议案引用某历史决议就视为取得该决议 |

关联状态 confirmed / candidate / unlinked 表示证据对关系的支持程度，没有固定相似度或线索数量可以自动升级为confirmed。矛盾未解释时保留候选。某主体会议较多、另一个较少是正常资料特征，不能建立第N次党委会对应第N次董事会的规则。

一个事项可以关联多次会议和多个版本；一份会议文件可有多个事项。判定者保留原 subject_ref，另建 matter_id。事项拆分/合并需要明确范围证据，不能强制一对一。会议页眉与本文件议题的对应也须记录，不能把别的会议日期套给当前议题。

### 4.2 每次比较先检查可比条件

只有确认了相关联结、主体/对象、比较的属性、业务阶段与版本关系、计量口径和实际精度，才能作确定性比较。跨阶段并非一律不比较，但要选对关系：申请→批准比较“决策怎样调整”，记录→同次纪要比较“是否忠实反映同一决定”，实际支出→批准额度比较“是否超限”。

| 比较目的 | 典型字段 | 运算及必要条件 | 不够时如何输出 |
|---|---|---|---|
| 通知与实际议题 | S agenda.title/number、schedule.change；R/M agenda.title | 在同场会议和明确议题关系中做集合及变更核对；议案申请也可作中间线索 | 议题候选对应或缺变更资料→insufficient，不直接说临时违规上会 |
| 前后顺序 | S/P/R/M各日期字段 | 使用实际事件日期；按规则选择strict_before/before_or_same；精度与事实性质必须支持该关系 | 同日无时刻不能证明严格先后；计划日期不能当实际日期 |
| 金额一致或限额 | financial.amount | 同币种、同对象范围、同口径；用Decimal留存单位换算；明确比较eq/le/变化，不猜汇率/税差 | 口径不同→not_comparable；口径未知→insufficient；缺值不作零 |
| 投票与到会 | R/M attendance.person/count、voting.count/expression | 依已确认规则确定分子分母；去重须有身份依据；列席不计表决权 | 仅有“一致通过”不能推得赞成票数；分母缺失→insufficient |
| 决策含义和条件 | R/M decision.content、condition.content；P proposal.action | 按动作、对象、金额、条件、否定、责任/期限逐项比；同时检查补正版本 | 语义相似不等于等价；缺条件先识别差异并核原文，再判义务 |
| 附条件落实 | R/M condition.content、follow_up.*；获准执行证据 | 确认条件触发、期限、履行证据与实际实施时间；安排与实际行为分开 | 当前只有会议资料时，列补证线索，不认定条件已经或未被履行 |

日期可视为时间区间：日期粒度涵盖当日全部时间，月份粒度涵盖整月。只有 A 的最晚可能时点仍早于 B 的最早可能时点，才足以支持严格先后；区间重叠保留不确定。规则如按自然日或工作日计算，需确认计时起点、是否包含当日及工作日日历；不默认相差1日就满足“提前1个工作日”。

金额换算仅由判定者在 comparisons 中留痕，如100万元→1000000元。原始 items.normalized 仍为100。不得把资本金与总投资、项目总额与单笔支付、含税与不含税、额度上限与预算估算直接作相等比较。判断调整有无授权，还需另外匹配规则和调整资料。

### 4.3 比较结果不等于业务结论

| comparison.result | 含义 | 后续 |
|---|---|---|
| consistent | 现有证据支持本次明确的比较关系，如同次决议金额一致 | 仅该比较关系成立，不代表所有内控要求符合 |
| different | 已有可比事实且关系不成立，如记录批准100而同次纪要写120 | 先核对原件、版本、例外；有适用义务才可能形成偏差 |
| insufficient | 关键字段、关联、精度、身份或口径不明确 | 指出需要补齐什么，不能当不同或相同 |
| not_comparable | 证据表明所选直接比较关系不适合，如项目总投资对单笔支付 | 改选正确关系，或另做有依据的检查 |

没有字典项时不得直接输出different。field_checks.not_found表示在说明范围内没提取到；只有完成该范围核验后，才可说材料缺该记载；实际义务未履行还需要相应证明。

## 5. 判定关联、比较和扫描协议

适配判定提示词/schema 1.3。保留 matters/decisions/leads/coverage，并使用以下关联与比较字段：

- `dictionary_version`：本次字段字典版本。
- `links[]`：link_id、relation（same_meeting / same_matter / same_event / same_group / revises / references）、left_subject_ref、right_subject_ref（各含run_id、subject_ref）、status（confirmed / candidate / unlinked）、evidence_refs（各含run_id、record_id、item_index）、basis、contradictions（字符串数组）。same_group 是对称的共同计划/预算/需求组关系，各事项保留独立 matter_id，不替代 same_matter/same_event。revises方向固定为左端新版本修订右端旧版本；references为左引用右。历史原件未提供时，不伪造右端引用，在对应事项uncertainty和requests中说明。
- `comparisons[]`：comparison_id、matter_id、link_ids、dimension（比较目的）、operator（eq / le / strict_before / before_or_same / set_compare / semantic / change_trace）、input_refs（各含run_id、record_id、item_index）、preconditions（逐项说明是否可比）、normalization（含原值、目标口径、换算或别名依据的文字数组）、calculation（数值计算或简明语义核对说明）、result（四值）、reason、limits（字符串数组）。没有跨文件关系的单源检查可以link_ids=[]并写明理由；不能藉此绕过依赖的跨源关联。
- matters 增加 link_ids；decisions 增加 comparison_ids。不需要字段比较的规则可留空数组，说明直接证据判断的依据。不得为了凑表强造比较。

累计比较仍在 comparison.preconditions/calculation 中列明成员事项、入组依据、累计期间/范围和排除项，input_refs 精确指向各自事实；matter_id 指本检查所评价事项，不重建一个假定的“合并事项”。共同计划本身不证明规则要求累计，也不证明存在规避。

lead_scan 保留事实触发与处置的区别：schema 1.3 每条新增必填 linked_decision_ids 数组。lead_found 要求 lead_ids 或 linked_decision_ids 至少一者非空；转入 CONTROL 时链接本判定 run 内同 matter_id 的 decision，可不另造重复 lead。其他扫描状态两数组均为空。状态为 lead_found 不自动等于偏差，关联次数不计作新增缺陷；具体契约见 [rule_judge](../prompts/rule_judge.md)。

只有已确认的关联能够支撑依赖该关系的确定性结论；candidate/unlinked仍可生成insufficient记录和补证问题。判定者派生的关联、运算不写回四路事实包。独立复核逐项检查这些新增记录。

## 6. 一个完整的串联示例（全部为虚构资料）

假设原文和正式事项编号足以确认这些材料对应A项目一期、同次董事会决定，且无相反的版本证据：

| 来源 | 独立提取 | 判定者怎样使用 |
|---|---|---|
| S通知 | 原文议题A项目一期，拟上会日期 | 核对议题安排；不当作已经批准 |
| P议案 | 申请人民币120万元，stage=requested | 保留申请值；与批准100万元形成change_trace，不判记录失真 |
| R记录 | 批准投资上限人民币100万元；实施前补充测算 | amount为100万元；condition单列并与决定关联 |
| M纪要 | 批准投资上限人民币120万元；未检出上述条件 | 与R同次决定金额eq比较为different；条件差异先回看完整决定段 |

判定路径：确认关系→核实金额口径→100与120同为批准上限→检查正式更正或再次决策→核对规则是否要求准确传达决议→给出符合/偏差/证据不足等初步结果。若补正纪要已有效改为100并保留条件，应保留变更历史并按规则分别评价原始差异及补正，不掩盖也不重复计数。

只凭这四份材料，不能说已经支付120万元、已经造成20万元损失、或者未做测算就实施。应提出“是否已实施、执行依据为何、测算何时完成”的中性问题，并索取对应执行证据。

## 7. 复核和回退

字段错提/漏提→主控以新run和新上下文，给对应角色中性问题及原件重新识别；不附本表期待结果。来源身份丢失→退资料处理。关联或运算错→退判定者修订。业务参数/效力不清→退base_rule和人工第二步。字典未覆盖→保留fact.other与扩展请求，修改字典需新版本，不在同一运行中悄悄变义。

共享定义可以预载入，共享推断不能进入四路上下文。程序校验只能识别结构、枚举、引用、时间索引等错误，不能证明字段与现实相符、所有信息无遗漏或技术访问隔离已实现。

来源版本/hash、连续引文分条和局部重跑有效采用规则统一见 [工作流](workflow.md)。同源副本不算独立佐证；重新提取不覆盖旧运行，受影响判断和旧复核须按依赖失效处理。
